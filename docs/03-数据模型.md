# 03 · 数据模型

> 本文的 SQL 是**规格说明**，不是最终代码。实现时按此建表，字段名与语义以本文为准。

## 1. 存储布局

所有数据在 `app.getPath('userData')` 下：

| 平台 | 实际路径 |
|---|---|
| Linux | `~/.config/my-deepseek-chat/` |
| macOS | `~/Library/Application Support/my-deepseek-chat/` |
| Windows | `%APPDATA%\my-deepseek-chat\` |

```
<userData>/
├── config.json      # 非敏感设置（JSON，可手改）
├── secret.json      # 仅 { enc: <base64> } 或 { plain: <string> }（降级时）
├── chat.db          # SQLite 主库（+ chat.db-wal / -shm）
├── logs/            # electron-log 滚动日志
└── models.json      # /models 拉取结果缓存（离线兜底）
```

**为什么配置用 JSON、数据用 SQLite**：配置需要人手改、跨版本稳定、体积极小；会话需要事务、索引、全文检索、增量写入。二者混用会让两边的优点都丢掉。

### 1.1 config.json 也有版本

`chat.db` 用 `PRAGMA user_version` 管迁移，`config.json` 用 `version` 字段管迁移，两者独立：

| 版本 | 变更 | 迁移动作 |
|---|---|---|
| 1 | 初版 | — |
| 2 | 深度思考默认改为开启 | 加载旧配置时一次性把 `defaultThinking` 置为 `true`，随后写回 `version: 2` |

规则：

- 迁移只在**加载时**执行一次，之后写回文件，用户后续手动改动不会被覆盖
- 迁移失败（JSON 损坏/字段非法）不是崩溃，而是回退到默认值并覆盖写回（配置可重建，对话不可重建——两者的失败策略不同）
- 与 DB 迁移一样，**已发布的版本分支不许回头改**：要给新装用户不同的初值，请加新版本号

## 2. 连接与 PRAGMA

```
PRAGMA journal_mode = WAL;      -- 流式期间持续写，WAL 避免读写互斥
PRAGMA synchronous  = NORMAL;   -- WAL 下足够安全，性能更好
PRAGMA foreign_keys = ON;       -- 必须显式打开，级联删除依赖它
PRAGMA busy_timeout = 5000;
PRAGMA user_version              -- 迁移版本号，见 §6
```

## 3. Schema

### 3.1 `sessions`

```sql
CREATE TABLE sessions (
  id              TEXT PRIMARY KEY,                 -- uuid v7（时间有序，利于排序与索引）
  title           TEXT NOT NULL DEFAULT '新对话',
  model_id        TEXT,                             -- NULL = 用全局默认
  thinking        INTEGER,                          -- NULL=继承全局 / 0=关 / 1=开
  effort          TEXT,                             -- NULL / low / high / max
  system_prompt   TEXT,
  temperature     REAL,                             -- NULL = 用全局默认
  max_tokens      INTEGER,                          -- NULL / 0 = 不限制
  active_leaf_id  TEXT,                             -- ★ 主线游标：当前展示的末端消息
  created_at      INTEGER NOT NULL,                 -- epoch ms
  updated_at      INTEGER NOT NULL,
  archived_at     INTEGER
);

CREATE INDEX idx_sessions_updated ON sessions(archived_at, updated_at DESC);
```

### 3.2 `messages`（树）

```sql
CREATE TABLE messages (
  id           TEXT PRIMARY KEY,
  session_id   TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  parent_id    TEXT REFERENCES messages(id) ON DELETE CASCADE,  -- NULL = 根
  role         TEXT NOT NULL CHECK (role IN ('system','user','assistant')),
  content      TEXT NOT NULL DEFAULT '',
  reasoning    TEXT,                                -- ★ reasoning_content，必须落库
  status       TEXT NOT NULL DEFAULT 'complete'
               CHECK (status IN ('streaming','complete','aborted','error')),
  model_id     TEXT,
  finish_reason TEXT,                               -- stop / length / aborted
  error_json   TEXT,                                -- { code, message }
  tokens_json  TEXT,                                -- 见 §3.5
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL
);

CREATE INDEX idx_msg_thread  ON messages(session_id, parent_id, created_at);
CREATE INDEX idx_msg_parent  ON messages(parent_id);
CREATE INDEX idx_msg_status  ON messages(status) WHERE status = 'streaming';
```

**为什么是树而不是线性数组**

- 线性数组把"重新生成"实现成 `UPDATE`，历史回答永久丢失，且将来加"编辑任意消息并分叉"时整张表要重建。
- 树上"重新生成"= 插入一个与旧回答同 `parent_id` 的新节点，然后改 `sessions.active_leaf_id` 指向它。**旧版本零成本保留。**
- v1 界面只展示主线，用户无感；`‹1/2›` 版本切换器与编辑分叉已在 v1.1 基于同一套查询落地。

**编辑即分叉（v1.1）**：编辑用户消息**不改原行**，而是在同一个 `parent_id` 下插入一条新的 user 兄弟节点，并为其生成新的 assistant 子节点；`active_leaf_id` 移到新分支末端。原消息与旧分支整条留在库里，可用该用户消息的 `‹1/2›` 切回。助手消息不提供编辑（走重新生成 / 版本切换）。

### 3.3 `usage_log`

```sql
CREATE TABLE usage_log (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id        TEXT REFERENCES sessions(id) ON DELETE SET NULL,
  message_id        TEXT,
  model_id          TEXT NOT NULL,
  prompt_tokens     INTEGER NOT NULL DEFAULT 0,
  completion_tokens INTEGER NOT NULL DEFAULT 0,
  reasoning_tokens  INTEGER,
  cache_hit_tokens  INTEGER,
  cache_miss_tokens INTEGER,
  duration_ms       INTEGER,               -- 首帧到结束
  first_token_ms    INTEGER,               -- 发起首 token 的延迟
  created_at        INTEGER NOT NULL
);

CREATE INDEX idx_usage_session ON usage_log(session_id, created_at);
CREATE INDEX idx_usage_time    ON usage_log(created_at);
```

v1 UI 只消费最近一次的 `usage` 帧；这张表为 v1.1 的费用仪表盘预留，并且**现在就开始写**，否则以后没有历史数据可看。

### 3.4 `kv`

```sql
CREATE TABLE kv (
  key        TEXT PRIMARY KEY,
  value      TEXT NOT NULL,   -- JSON 字符串
  updated_at INTEGER NOT NULL
);
```

用途：`models_cache`、`schema_meta`、`last_selected_session`、UI 分栏宽度等不适合进 `config.json` 的运行态。

### 3.5 `tokens_json` 结构

```json
{
  "prompt": 12480,
  "completion": 860,
  "reasoning": 1320,
  "cacheHit": 11000,
  "cacheMiss": 1480,
  "firstTokenMs": 620,
  "durationMs": 8400
}
```

字段名与 `usage` 帧保持 camelCase 一致，避免渲染层做映射。

## 4. 核心查询

### 4.1 加载主线（v1 唯一的读取路径）

从 `active_leaf_id` 向上回溯再反转。用递归 CTE，深度 = 消息数：

```sql
WITH RECURSIVE thread(id, parent_id, role, content, reasoning, status,
                      model_id, tokens_json, error_json, created_at, depth) AS (
  SELECT id, parent_id, role, content, reasoning, status,
         model_id, tokens_json, error_json, created_at, 0
  FROM messages WHERE id = :leafId
  UNION ALL
  SELECT m.id, m.parent_id, m.role, m.content, m.reasoning, m.status,
         m.model_id, m.tokens_json, m.error_json, m.created_at, t.depth + 1
  FROM messages m JOIN thread t ON m.id = t.parent_id
)
SELECT * FROM thread ORDER BY depth DESC;
```

若 `:leafId` 为 `NULL`（空会话），返回空数组。

### 4.2 发送后置顶会话

```sql
UPDATE sessions SET updated_at = :now,
       active_leaf_id = COALESCE(:newLeaf, active_leaf_id)
WHERE id = :sessionId;
```

### 4.3 启动自愈（★ 崩溃安全的关键）

```sql
UPDATE messages
SET status = 'aborted', updated_at = :now
WHERE status = 'streaming';
```

任何 `streaming` 残留都意味着上次进程没正常结束。启动时统一标记为 `aborted`，UI 提示「上次生成被中断，可重试」。因为流式期间每 200ms 就落库，**最坏只丢最后 200ms 的输出**。

### 4.4 兄弟版本（为 v1.1 的版本切换预留）

```sql
SELECT id FROM messages
WHERE session_id = :sid AND parent_id IS :pid AND role = 'assistant'
ORDER BY created_at;
```

## 5. 写入策略（先建后补）

```
chat:send
  ├─ 1. INSERT user 消息        (status='complete')
  ├─ 2. INSERT assistant 消息   (status='streaming', content='')  ← 先拿到 id
  └─ 3. 返回 { requestId, userMessageId, assistantMessageId }  ← 立即返回，UI 先渲染空壳

流式过程中
  └─ FlushScheduler: 每 200ms 或累计 32 帧，UPDATE messages
       SET content=?, reasoning=?, updated_at=? WHERE id=?
     （单条 UPDATE，WAL 下开销可忽略）

终态
  ├─ 强制 flush（确保尾部字符不丢）
  ├─ UPDATE status='complete'|'aborted'|'error', tokens_json=?, finish_reason=?
  ├─ INSERT usage_log
  └─ UPDATE sessions SET updated_at=?, active_leaf_id=assistantMessageId
```

**为什么不是"流完再 INSERT 整条"**：那样一旦崩溃，整轮回答全丢。先 INSERT 后增量 UPDATE 的代价只是多一次 `UPDATE` 语法，收益是数据不丢。

## 6. 迁移机制

`PRAGMA user_version` 存已应用的迁移序号，代码里按数组顺序执行缺失项，全部包在一个事务中：

```
user_version = 0  → 应用 001_init           → user_version = 1
user_version = 1  → 应用 002_add_fts        → user_version = 2   (v1.1)
```

规则：

- 迁移函数**只向前**，不写 down
- 每条迁移必须是幂等安全的或在事务内原子完成
- 破坏性变更（删列）在 SQLite 中通过"建新表 → 拷数据 → 删旧表 → 改名"完成
- 迁移前自动备份 `chat.db` 为 `chat.db.bak.<user_version>`，保留最近 3 份

## 8. 数据生命周期

| 事件 | 动作 |
|---|---|
| 删除会话 | `DELETE FROM sessions WHERE id=?` → 级联删消息；`usage_log` 置 `session_id=NULL` 保留统计 |
| 归档会话 | 只写 `archived_at`，`updated_at` 不动（恢复后回到原位）；不在主列表与搜索结果中出现，左栏「已归档」可恢复；全量导出仍包含 |
| 重新生成 | 新增 assistant 兄弟节点，旧节点保留（可通过导出看到全部版本） |
| 版本切换（v1.1） | 改 `active_leaf_id`，不删数据。游标落到**目标版本分支的最新末端**（沿最新子节点一路向下），因此原分支上更靠后的消息会移出主线但仍留在库里 |
| 编辑消息（v1.1） | 在同 `parent_id` 下插入新的 user 兄弟节点 + 新 assistant 子节点，游标移到新分支末端；原消息不改不删，可用 `‹1/2›` 切回 |
| 清空全部数据 | 设置页危险操作，需输入 `DELETE` 确认；删库后重建并重新迁移 |
